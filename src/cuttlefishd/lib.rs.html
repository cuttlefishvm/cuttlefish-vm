1//! The cuttlefish daemon: accepts delegated jobs, runs them, streams results.
2//!
3//! The transport decision is recorded here, because it is the choice most
4//! likely to be revisited by someone who was not present for it.
5//!
6//! # Transport: HTTP over a unix domain socket
7//!
8//! Clients talk to the daemon over HTTP on a unix domain socket, with
9//! server-sent events for live job output.
10//!
11//! It is worth being precise about what that does and does not mean, because
12//! "why HTTP instead of IPC?" is the obvious question and it contains a false
13//! dichotomy. A unix domain socket *is* inter-process communication. The socket
14//! was never in question; HTTP is only the framing carried over it. The real
15//! choice is which protocol rides the socket.
16//!
17//! HTTP was chosen for reasons that all reduce to *nobody has to write protocol
18//! code*:
19//!
20//! - Every language has a mature client, so consuming cuttlefish costs no
21//!   bespoke implementation. The CLI in this workspace is a thin wrapper around
22//!   an off-the-shelf HTTP client.
23//! - It is debuggable by hand. `curl --unix-socket` reproduces any client
24//!   interaction, which matters enormously while the reactor loop and the
25//!   capability model are still being proven.
26//! - Server-sent events supply streaming *and* `Last-Event-ID` replay. The
27//!   replay half is not incidental: a client that submits a job and then
28//!   connects to the event stream would otherwise miss everything a fast job
29//!   emitted in between.
30//! - Exposing the daemon over TCP for a remote caller becomes a config change
31//!   rather than a second protocol.
32//!
33//! ## The alternative, and the one argument that genuinely favours it
34//!
35//! A leaner framing — length-prefixed JSON, JSON-RPC, gRPC — would cost less per
36//! message and would be bidirectional, letting cancellation travel in-band
37//! instead of as a separate `DELETE`. Neither matters much here: this transport
38//! carries jobs, not packets, and cancellation is rare.
39//!
40//! JSON-RPC deserves a specific mention as the strongest of those: it is what
41//! MCP and LSP speak, so it is the framing that agent tooling already
42//! understands, and adopting it would leave cuttlefish a short step from being
43//! usable directly as an MCP server.
44//!
45//! The genuinely compelling argument for a raw socket protocol, though, is one
46//! HTTP cannot answer at all: **file descriptor passing**. A unix socket can
47//! transfer an open file descriptor via `SCM_RIGHTS`. For this project that is
48//! not a micro-optimisation, it changes the security model:
49//!
50//! - Today a caller passes a *path*, the daemon checks it against the job's
51//!   granted capabilities, and then opens it. Check and open are separate
52//!   syscalls, so there is a window in which the path can be swapped —
53//!   precisely the race that symlink attacks exploit.
54//! - If the caller passed an already-open descriptor instead, there would be no
55//!   window, because the descriptor *is* the capability. The daemon would need
56//!   no filesystem access to the path at all, which is a materially stronger
57//!   version of the privacy guarantee this project exists to provide.
58//!
59//! A related, smaller benefit: `SO_PEERCRED` lets the daemon establish the uid
60//! and pid of its peer, which matters on a shared machine.
61//!
62//! Neither of these is a reason to replace the control plane. Descriptor
63//! passing cannot ride HTTP no matter what else is decided, so it needs a side
64//! channel in *every* design — which makes it additive later rather than a
65//! constraint now. The path-based capability check keeps its own defence in the
66//! meantime: it canonicalises both sides before comparing, which closes the
67//! traversal and symlink cases it can close without descriptor passing.
68//!
69//! Revisit this decision if descriptor passing becomes required, or if
70//! cuttlefish should speak MCP natively. Do not revisit it for performance
71//! without a measurement showing the transport is the bottleneck; at job
72//! granularity it will not be.
73

82/// Scan every job directory under `jobs_root` for a ledger whose
83/// `job_status` is still `Running` — i.e. a job that was mid-flight when the
84/// daemon last stopped — and record it in `jobs` as [`cuttlefish_abi::JobStatus::Interrupted`].
85///
86/// Called once at startup, and directly by tests that build a `JobStore`
87/// without going through `main()`. Nothing here resumes a job automatically:
88/// see the "Resume is a signal, not an automatic action" section of the
89/// design doc. `current_fingerprint` is passed through to `Ledger::open`,
90/// but is only meaningful for a ledger that doesn't exist yet — every ledger
91/// this loop opens already exists (its presence is what selected the
92/// directory), so the value recorded at that ledger's original creation is
93/// what's read back, untouched.
94///
95/// A single job directory whose ledger can't be opened or read (e.g.
96/// corrupted by a hard crash mid-write) is logged and skipped, not treated
97/// as fatal — the whole point of this scan is to surface crash damage, so it
98/// must not itself go down because of the very class of crash it looks for.
99/// Only a failure to list `jobs_root` at all is fatal, since that means the
100/// scan cannot proceed in any capacity.
101pub async fn scan_for_interrupted_jobs(
102    jobs_root: &std::path::Path,
103    current_fingerprint: &str,
104    jobs: &state::JobStore,
105) -> anyhow::Result<()> {
106    if !jobs_root.exists() {
107        return Ok(());
108    }
109    for entry in std::fs::read_dir(jobs_root)? {
110        let entry = entry?;
111        let ledger_path = entry.path().join("ledger.sqlite");
112        if !ledger_path.exists() {
113            continue;
114        }
115        let id = entry.file_name().to_string_lossy().into_owned();
116        let ledger = match cuttlefish_host::ledger::Ledger::open(&ledger_path, current_fingerprint)
117        {
118            Ok(l) => l,
119            Err(e) => {
120                eprintln!(
121                    "warning: could not open ledger for job `{id}` at startup scan, skipping: {e}"
122                );
123                continue;
124            }
125        };
126        match ledger.job_status() {
127            Ok(cuttlefish_host::ledger::LedgerJobStatus::Running) => {
128                jobs.mark_interrupted(id).await;
129            }
130            Ok(_) => {}
131            Err(e) => {
132                eprintln!("warning: could not read job status for job `{id}` at startup scan, skipping: {e}");
133            }
134        }
135    }
136    Ok(())
137}
